# External SMTP sender — implementation work, not deployed

The requested Settings flow must accept Name, Email, Server, Username and Password, test the connection, and make successfully connected senders available in the composer From dropdown without changing existing senders. Port 587 with STARTTLS and port 465 with implicit TLS are proposed; make port and security explicit in the UI. Cloudflare Workers block outbound port 25; some destinations (including private IPs and Cloudflare IP ranges) are also blocked. A successful authentication test is not proof that sending or delivery works.

## Work present in this branch

`src/external-smtp-config.mjs` contains input validation and AES-GCM credential encryption helpers, bound to both account ID and connection ID. `test/external-smtp-config.test.mjs` tests input rejection, encryption, nonce uniqueness, tamper detection and cross-account binding. Neither is routed, persisted, used by the queue, or deployed. Hostname validation is not DNS/IP validation and does not establish protection from rebinding. Do not connect sockets based only on this validator.

## Remaining production requirements

- Add an account-scoped connection store, authorization and ownership checks on every list/create/update/test/delete/use. Store credentials only as encrypted ciphertext with a securely provisioned, versioned encryption key, rotation and backup/recovery procedure. Never log or return passwords or ciphertext in normal APIs; editing a sender should not disclose its stored password. Validate body sizes and same-origin protections; add cross-account negative tests.
- Protect outbound connection tests and sending against private, loopback, link-local and metadata destinations, including DNS rebinding and multi-address DNS answers; preserve TLS certificate and hostname verification. Establish how the runtime enforces resolved-address policy at connection time before enabling arbitrary hosts. Restrict outbound ports and require TLS before authentication.
- Run a bounded, rate-limited connection test with explicit pending, success, authentication failure, TLS failure, unreachable and timeout states. Report only verified, account-specific observable outcomes. No test should send mail or reveal secrets. Re-test or disable the connection after edits; only currently verified configurations appear as selectable senders.
- On send, authorize the selected connection by the signed-in account and store only its ID with the durable message/batch. Resolve encrypted credentials server-side at dispatch. Keep existing suppression rules, recipient-specific claims, queue controls, attempt limits and unknown-outcome reconciliation; never blindly retry an uncertain DATA result. Do not apply the existing transport's provider-specific headers or delivery-event assumptions to external SMTP. Deleting or changing a connection must not silently redirect already queued messages.
- Implement create, edit, test, remove, and sender-dropdown UI with accessible labels, loading states, disabled duplicate submissions, safe errors, mobile layout and optional cancellation. Never print or prefill a saved password. Preserve existing logo and sender options.
- Add end-to-end server tests for account isolation, validation, encryption, credential rotation, SSRF, DNS changes, TLS, timeouts, connection test, queue outcomes and sender ownership; add browser, Android WebView and real authorized test-server acceptance. Review desktop/mobile screenshots. Deploy migrations and secret configuration with rollback only after readiness gates pass.

## Settings: LeadMASTER-only SMTP monitoring

Provide a per-connected-sender monitoring view using only messages and events generated by LeadMASTER. It must not import the external provider's inbox, provider-wide sending history, account statistics, or unrelated applications' activity. Show real counts and a bounded, paginated history of LeadMASTER submissions, with timestamps and states such as queued, accepted by SMTP, failed and outcome unknown. Accepted is not delivered; show delivery only if an actual account-scoped delivery signal is available. Include loading, empty, error and refresh states and make clear when data is unavailable.

The dispatcher must record account-owned, connection-owned, idempotent submission transitions and correlate them to LeadMASTER message IDs. Provide authenticated, tenant-scoped read queries with appropriate retention, access controls and limits. No SMTP credentials, passwords, message bodies or other accounts' events may appear in logs or monitoring responses. Verify that deletion/reconfiguration of a sender cannot expose or misattribute prior history. This monitoring UI, event ledger, aggregation and retention policy do not exist yet and are not deployed.
