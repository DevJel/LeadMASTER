# Dispatch-time suppression review — candidate only

The existing producer checks `email_unsubscribes` when a request is queued. This does not cover an address added to that list while a message waits. This candidate consumer rechecks the same global list immediately before SMTP for both admin and developer sends. A suppressed message is marked `failed` with `suppressed_at_dispatch`; it is not submitted to SMTP. The admin message-detail API exposes the reason and the candidate dashboard shows it alongside the message body. A duplicate delivery does not resend.

The first read occurs before the durable send claim so an unavailable suppression table fails closed and retries without creating a fence. A second read after the claim narrows the check-to-send interval. If that read fails, no SMTP call occurs, but the `started` fence remains for manual reconciliation, like other ambiguous claims. A failed final D1 transaction likewise requires reconciliation, and may leave an unconfirmed record even when no SMTP call occurred. Do not blindly retry.

**Limit:** This does not eliminate the race in which suppression is added after the final read and before SMTP submission; strict no-send-after-suppression requires a coordinated delivery/opt-out design and cannot be guaranteed by two independent D1 reads plus an external SMTP call. The existing suppression list is global, not account-scoped; this change preserves current semantics and does not prove multi-tenant isolation or consent. No change to login/security-alert SMTP traffic is included. This is neither a campaign system nor a global rate limiter.

Local SQLite tests include suppression after enqueue for both sources, mixed-case matching, duplicate queue delivery, missing table, a suppression inserted between checks, and a failed post-claim read. Existing send-fence, error and pacing tests also pass. An actual Cloudflare Worker/D1 queue, SES receipt, migration rollout, production schema and real concurrent opt-outs have not been tested. Do not deploy until the 0009/0010 migration and old-consumer drain, reconciliation, staging, backup and rollback gates are complete and a targeted production release is approved. No real email was sent during these tests.
